# Fase 04.1: Relatório de Code Review

**Revisado em:** 2026-10-15T09:30:00Z
**Profundidade:** standard
**Arquivos revisados:** 50
**Status:** issues_found

## Resumo

Revisão adversarial do redesign "Aurora técnica" (componentes, scripts de efeito, CSS de tokens/motion, coleções de conteúdo, gates de verificação e CI). As regras do projeto foram respeitadas: não há atributos `style=`, não há comentários nos arquivos versionados, todo `target="_blank"` leva `noopener` e o conteúdo fica visível sem JS (o gate `nojs` confirma).

Mesmo assim, dois defeitos foram **confirmados empiricamente** com Playwright contra o build em `.vercel/output/static`:

1. O formulário de orçamento, ao ser enviado, faz `GET /?nome=…&email=…`. O pedido se perde em silêncio e os dados pessoais vão parar na URL.
2. O efeito de tilt dos cards (`tilt.ts`) nunca aparece, porque uma regra de reveal com especificidade maior o sobrescreve.

Entre os warnings, também confirmados em navegador: deslocamento de layout de 16px quando o header encolhe, estado ativo da navegação que nunca é limpo e uma classe de delay inexistente (`d320`).

Os gates de navegador passaram sem detectar nenhum desses problemas, o que mostra pontos cegos na cobertura (WR-07).

## Critical Issues

### CR-01: Formulário envia dados pessoais por GET para `/` e descarta o pedido em silêncio

**Arquivo:** `src/components/ContactSection.astro:110`
**Problema:** O `<form>` não tem `action` nem `method` e agora usa `novalidate`. Nenhum script do bundle (`effects.ts` → reveal/scroll/visibility/tilt) intercepta o `submit`. Com JS ligado ou desligado, o envio vira navegação GET para a própria página. Reproduzido:

```
after submit url: http://127.0.0.1:51991/?nome=Fulano&whatsapp=&email=fulano%40x.com&mensagem=
```

Consequências:
- **Perda de dados:** o visitante acha que pediu orçamento e o lead some, sem nenhum feedback.
- **LGPD / confidencialidade:** nome, e-mail, WhatsApp e mensagem ficam no histórico do navegador, nos logs de requisição da Vercel, no `Referer` de qualquer link externo clicado em seguida (WhatsApp, Instagram, PageSpeed) e, possivelmente, no beacon do `@vercel/analytics`, que roda sem `beforeSend` para remover a query string.
- **Sem validação:** o `novalidate` desligou até a validação nativa do `required` em `#nome` (a versão anterior a tinha).
- **UI morta:** os estados `.err`, `.err-contato`, `.sending`, `.done`, o botão "Enviar outro pedido" e a região `#form-status` com `aria-live` não têm nenhum código que os acione.

O backend está previsto para a Fase 5, mas este branch publica um formulário funcional na aparência e quebrado no envio.

**Correção:** até o endpoint existir, impedir que dados vão para a URL e deixar claro que o canal ainda não está ativo. Por exemplo:

```astro
<form class="form glass" id="form-orcamento" method="post" action="/api/orcamento" aria-labelledby="form-title" data-r="form">
```

Junto com isso, tirar `novalidate` enquanto não existir validador JS. Se o branch for publicado antes da Fase 5, a alternativa é esconder ou substituir o formulário pelos canais WhatsApp/e-mail. Em nenhuma hipótese manter um `<form>` sem `method="post"`.

### CR-02: Tilt dos cards nunca aparece (especificidade CSS anula `.settled`)

**Arquivo:** `src/components/ProjectsSection.astro:470-478` e `:498-504`; `src/scripts/tilt.ts`
**Problema:** A regra de reveal compila para
`html.js-ready .card[data-astro-cid-6iojtk56][data-r].in { transform:none; transition:… }`, com especificidade (0,5,1). A regra do tilt compila para
`.card[data-astro-cid-6iojtk56].tilt.settled { transform: perspective(900px) rotateX(var(--rx)) … }`, com especificidade (0,4,0).

Como a de reveal sempre vence, o `transform` fica `none` para sempre, inclusive a `transition` de 0.25s. Verificado com Playwright: o card recebe `in settled`, o JS grava `--rx: 3.60deg` e `--ry: 3.60deg`, mas `getComputedStyle(card).transform === 'none'`.

O resultado é que `tilt.ts` registra três listeners por card e um rAF a cada `pointermove` sem nenhum efeito visível. É um entregável da fase que não funciona.

**Correção:** dar à regra de tilt especificidade maior que a do reveal, ou tirar o `transform` do estado `.in` assim que o card estiver assentado:

```css
@media (pointer: fine) and (prefers-reduced-motion: no-preference) {
  :global(html.js-ready) .card.tilt[data-r]:global(.in.settled) {
    transform: perspective(900px) rotateX(var(--rx, 0deg)) rotateY(var(--ry, 0deg));
    transition: transform 0.25s ease, border-color 0.25s ease;
    transition-delay: 0s;
  }
}
```

Também vale incluir um gate de navegador que passe o ponteiro sobre `.card.tilt` e verifique `transform !== 'none'`.

## Warnings

### WR-01: Header encolhe 16px no fluxo e desloca a página inteira (layout shift ao rolar)

**Arquivo:** `src/components/SiteHeader.astro:90-103`
**Problema:** `.site-header` é `position: sticky` e por isso ocupa espaço no fluxo. Quando `scrollY > 24`, `.header-inner` passa de `height: 84px` para `68px` com transição de `height`. Todo o conteúdo abaixo sobe 16px além da rolagem. Medido: `#servicos` foi de 709px para 683px ao rolar só 10px, ou seja, 16px de deslocamento extra. Isso conta como layout shift no CLS de campo (scroll não é uma entrada que exclui shift) e anima uma propriedade de layout quadro a quadro. Em páginas curtas (404/obrigado), a faixa de rolagem pode ficar menor que o limiar e o header alternar entre os dois estados.
**Correção:** manter a altura do header constante e animar só o visual (por exemplo, `padding` dentro de uma caixa de altura fixa, ou `transform: scale` na marca), ou tirar o header do fluxo (`position: fixed` + espaçador de 84px).

### WR-02: Mensagens de erro sempre anunciadas como descrição dos campos

**Arquivo:** `src/components/ContactSection.astro:124-154`
**Problema:** `aria-describedby="erro-nome"`, `"… erro-whatsapp"` e `"… erro-email"` apontam para `<span class="msg">` com `display:none`. Elementos referenciados por `aria-describedby` entram na descrição acessível mesmo ocultos, então o leitor de tela anuncia "Informe seu nome para sabermos com quem falamos." e "Use um e-mail completo…" ao focar cada campo, sem nenhum erro ocorrido. Como nenhum script aplica `aria-invalid`, o usuário de leitor de tela ouve um erro permanente.
**Correção:** só incluir o id do erro no `aria-describedby` quando houver erro (via JS, junto com `aria-invalid="true"`), ou separar uma dica estática (`id="dica-whatsapp"`) do texto de erro.

### WR-03: Classe `d320` não existe e inverte a ordem do reveal em "Sobre"

**Arquivo:** `src/components/AboutSection.astro:39`
**Problema:** `motion.css` define `.d200`, `.d300`, `.d450`, `.d520`, `.d680`, `.d700` e `.d820`, mas não `.d320`. O segundo `.lead` cai no fallback `var(--d, 0ms)` e aparece **antes** do primeiro. Medido: `transitionDelay` de `['0.2s', '0s']`. O gate `tokens` não detecta classes inexistentes.
**Correção:** usar `d300` (ou criar `.d320 { --d: 320ms; }` em `motion.css`).

### WR-04: Estado ativo da navegação nunca é limpo

**Arquivo:** `src/scripts/visibility.ts:27-39`
**Problema:** O observer só trata `isIntersecting === true`. Ao voltar para o hero, ou ao chegar em `#contato` (que não tem `data-nav`), o último link continua `.on`. Verificado: rolando até `#sobre` e voltando ao topo, `Serviços` fica destacado com o usuário no hero.
**Correção:** limpar todos os `.on` quando nenhuma seção rastreada cruzar a faixa central. Por exemplo, manter um `Set` das seções visíveis e, se ele ficar vazio, remover `.on` de todos os links; ou incluir o hero e o contato como alvos que zeram o estado.

### WR-05: Hover do serviço herda o atraso escalonado do reveal no `<h3>`

**Arquivo:** `src/components/ServicesSection.astro:235-248`
**Problema:** A regra `.svc-list.in .svc h3` define `transition` para `opacity, translate, transform` com um **único** `transition-delay: calc(var(--i) * 110ms)`, que vale para as três propriedades. O `p` foi corrigido com três valores (linha 247), mas o `h3` não. No hover/focus-within, o `h3` do 4º item só desliza depois de 330ms, enquanto `p` e `svg` deslizam na hora.
**Correção:**
```css
:global(html.js-ready) .svc-list.in .svc h3 {
  transition-delay: calc(var(--i) * 110ms), calc(var(--i) * 110ms), 0s;
}
```

### WR-06: Card em destaque sugere clique, mas não é interativo

**Arquivo:** `src/components/ProjectsSection.astro:44-87`, `:239-243`
**Problema:** `.c-feat` tem uma seta em círculo que inverte as cores e gira no `:hover`, `cursor` padrão, e não tem `<a>`. O visitante tenta clicar e nada acontece. O `coverAlt` (validado com `min(5)` no schema) também fica dentro de `.browser[aria-hidden="true"]`, então nunca é exposto.
**Correção:** transformar o título em link para o case ou para `https://agenciadmarques.com.br` (com o padrão de "card clicável" via `::after` no link), ou remover a seta e o efeito de hover. Se o mock continuar `aria-hidden`, deixar de exigir `coverAlt` ou usar `alt=""`.

### WR-07: Gates de navegador com pontos cegos (não pegaram CR-01, CR-02 nem WR-03)

**Arquivo:** `scripts/verify/browser-gates.mjs:92-213`
**Problema:**
- `nojs`, `reduced` e `fallback` só checam `opacity` do **próprio** `[data-r]`. Os elementos realmente ocultos pela CSS dos componentes são descendentes: `.svc h3/p`, `.diffs > li`, `.next > li`, `.channels > .channel`, `.portrait` (`clip-path`) e os traços do svg. Uma regressão neles passaria.
- Nenhum gate exercita tilt, envio do formulário ou ordem dos delays.
- `fallback` remove só `<script type="module">` inline. Se o Astro deixar de inlinar `effects.ts` (bundle maior que o limite de inline), o script externo continua carregando e o gate passa a testar outra coisa sem falhar.

**Correção:** no `fallback`/`nojs`, verificar a opacidade efetiva e o `clip-path` de uma lista de seletores de descendentes; remover também `<script type="module" src=…>` na rota interceptada (ou bloquear `/_astro/*.js` via `page.route`); adicionar checagens de tilt (`transform !== 'none'` após hover) e de `form.method === 'post'`.

## Info

### IN-01: Teste importa `.ts` direto, incompatível com o `engines` declarado

**Arquivo:** `src/scripts/steps.pure.test.mjs:3`, `package.json:7-9`
**Problema:** `node --test` importando `./steps.pure.ts` depende do type stripping nativo, que é padrão só a partir do Node 22.18/23.6. O `engines` aceita `>=22.12.0`, então em 22.12–22.17 o `pnpm test` quebra. O CI usa Node 24 e não percebe.
**Correção:** subir `engines.node` para `>=22.18.0`, ou usar `--experimental-strip-types` no script `test`.

### IN-02: `tipoCurto` tipado como `Record<string, string>`

**Arquivo:** `src/components/ProjectsSection.astro:13`
**Problema:** se um novo valor entrar em `PROJECT_TYPE_VALUES`, a tag renderiza "Exemplo de escopo · undefined" sem erro de tipo.
**Correção:** `const tipoCurto: Record<ProjectType, string> = { … }` importando `ProjectType` de `../content/project-types`.

### IN-03: Campos de schema obrigatórios que nunca são renderizados

**Arquivo:** `src/content.config.ts:55-56`, `src/content/cases/dmarques.md`
**Problema:** `problema` e `solucao` (`min(40)`) e o corpo markdown do case não aparecem em lugar nenhum. É conteúdo obrigatório morto, que vai sair de sincronia com o que é exibido.
**Correção:** remover os campos e o corpo, ou torná-los `optional()` até haver uma página de case.

### IN-04: Utilitários de motion sem uso

**Arquivo:** `src/styles/motion.css:117-139`, `:13-111`
**Problema:** `.d300`, `.d450` e `.d700` não são usados em nenhum componente, e `.i9`–`.i24` também não são usados pelo conteúdo atual. Por outro lado, um título com mais de 25 palavras em `Words` ficaria sem `--i` (delay inválido). A lista fixa é frágil nos dois sentidos.
**Correção:** remover as classes sem uso e limitar ou validar a contagem de palavras em `Words.astro`.

### IN-05: Robustez dos scripts de verificação e captura

**Arquivo:** `scripts/verify/static-server.mjs:86-121`, `scripts/capture-site.mjs:11-12`
**Problema:** `startStaticServer` nunca rejeita: um erro em `listen` deixa a Promise pendente e o CI trava até o timeout do job. `CAPTURE_WIDTH`/`CAPTURE_QUALITY` não numéricos viram `NaN` e só falham dentro do sharp, com mensagem pouco clara. `capture-site` fotografa o build **anterior** e grava em `src/`, gerando uma dependência circular (a captura comitada sempre mostra o site de um build atrás).
**Correção:** `server.once('error', reject)`; validar os números com `Number.isFinite`; documentar no script que ele deve rodar depois de `pnpm build` e ser seguido de um novo build.

### IN-06: Detalhes de conteúdo e SEO nas páginas secundárias

**Arquivo:** `src/pages/obrigado.astro:13`, `src/pages/404.astro`, `src/components/SiteFooter.astro:7`, `src/components/HeroBleed.astro:40`
**Problema:**
- `/obrigado` diz "fale com a gente no WhatsApp" sem link na página (no desktop, `.wa-float` fica oculto).
- `/obrigado` e `/404` não têm `noindex`.
- O ano do rodapé é congelado no build.
- "Confira você mesmo" aponta para a raiz do PageSpeed, e não para `https://pagespeed.web.dev/analysis?url=https://agenciadmarques.com.br`, então a prova prometida exige trabalho do visitante.

**Correção:** adicionar o link do WhatsApp; aceitar uma prop `noindex` no `BaseLayout`; pré-preencher a URL do PageSpeed.

### IN-07: CSS duplicado entre as três páginas secundárias

**Arquivo:** `src/pages/404.astro:22-48`, `src/pages/obrigado.astro:23-49`, `src/pages/politica-de-privacidade.astro:21-54`
**Problema:** `.intro`, `.content-block`, `.actions` e o reset de `h1,p` estão copiados três vezes.
**Correção:** extrair para um componente `SimplePage.astro` ou para uma classe global em `base.css`.

### IN-08: Scripts inline vão exigir hashes manuais quando a CSP virar header (Fase 7)

**Arquivo:** `src/layouts/BaseLayout.astro:29-35`, `:44-46`
**Problema:** o `is:inline`, o `effects.ts` inlinado pelo Astro (`<script type="module">…`) e o inline do `@vercel/analytics` são três scripts inline. A CSP planejada em `vercel.json` (`script-src 'self'`, sem `security.csp`) vai bloqueá-los, a menos que os hashes sejam mantidos à mão. Se isso acontecer, `js-ready` nunca é aplicado e todas as animações somem em silêncio. Além disso, `var d` vaza para `window.d`, e `fx` é marcado antes de `initReveal`: se o reveal lançar exceção, o fallback de 3s fica desarmado e o conteúdo permanece oculto.
**Correção:** forçar o bundle externo (`build.assetsInlineLimit: 0` ou import em arquivo `.ts` dedicado) ou adotar `security.csp`; envolver o inline em IIFE; adicionar `fx` só depois de `initReveal(reduced)`.

### IN-09: Sombreamento do global `process`

**Arquivo:** `src/components/ProcessSection.astro:5`, `src/content.config.ts:18`
**Problema:** `const process = …` sombreia o global do Node, o que é confuso em arquivos que rodam no servidor e pode quebrar um uso futuro de `process.env` no mesmo escopo.
**Correção:** renomear para `steps` / `processCollection`.
