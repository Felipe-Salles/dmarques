## Pattern Assignments

### `src/content.config.ts` (config / schema module, build-time validate)

**Structural source:** `RESEARCH` Pattern 1, L257-343 (verified against `node_modules/astro@7.3.1` — `dist/content/config.d.ts`, `dist/content/loaders/*.d.ts`).
**Style source:** `astro.config.mjs` L1-13.

**Imports (mirror `astro.config.mjs` import style — single quote, named, subpath):**
```typescript
import { defineCollection } from 'astro:content';
import { glob } from 'astro/loaders';
import { z } from 'astro/zod';
import { PROJECT_TYPE_VALUES } from './content/project-types';
```
- `import { z } from 'astro/zod'` — **not** `from 'astro:content'`. The `astro:content` `z` re-export is marked `// TODO: remove in Astro 8` in the installed source (`RESEARCH` L106-107, L340-341). Both resolve to `zod/v4`.
- Drop `reference` from the import — unused in v1, no cross-collection links (`RESEARCH` L343).
- The relative import `./content/project-types` mirrors `BaseLayout.astro` L4 (`'../styles/tokens.css'`). Config file sits at `src/`, module at `src/content/`.

**Collection definition pattern (one per collection, 5 total):**
```typescript
const services = defineCollection({
  loader: glob({ base: './src/content/services', pattern: '**/*.yaml' }),
  schema: z.strictObject({
    order: z.number().int().positive(),
    titulo: z.string().min(3).max(60),
    descricao: z.string().min(20).max(180),
    icon: z.enum(SERVICE_ICONS),
  }),
});
```
- `z.strictObject({...})` — **never** `z.object(...).strict()` (deprecated in Zod 4; `RESEARCH` L432-433, L672-673). This is the CONTENT-01 "bad key fails the build" mechanism (`RESEARCH` L332-334).
- `defineCollection({...})` call shape parallels `defineConfig({...})` in `astro.config.mjs` — same 2-space body, trailing comma, no `type:` key (inferred from `loader`; `RESEARCH` L436-437).
- `glob({ base, pattern })` per collection: `pattern: '**/*.yaml'` for the four data collections, `'**/*.md'` for `cases`.
- Derive `SERVICE_ICONS` from an `as const` tuple in this file (icon-name values are Claude's discretion, follow design labels — `CONTEXT` D-03; `RESEARCH` L272).

**`cases` is the only schema-as-function** (needs `image`):
```typescript
const cases = defineCollection({
  loader: glob({ base: './src/content/cases', pattern: '**/*.md' }),
  schema: ({ image }) =>
    z.strictObject({
      titulo: z.string().min(3).max(80),
      rotulo: z.enum(['projeto próprio', 'demo']),
      tipo: z.enum(PROJECT_TYPE_VALUES),
      cover: image(),
      coverAlt: z.string().min(5).max(160),
      problema: z.string().min(40).max(600),
      solucao: z.string().min(40).max(600),
      resultado: z.string().min(40).max(600),
      order: z.number().int().nonnegative().default(0),
    }),
});
```
- Keep the four YAML schemas as **plain objects**, not functions — `image` is only provided in the function form; a plain-object schema calling `image()` throws `ReferenceError` at config load (`RESEARCH` Pitfall 2 L488-496).
- `cover: image()` **required**, not `.optional()` — `CONTEXT` D-08. Placeholder committed now.
- `tipo: z.enum(PROJECT_TYPE_VALUES)` — Zod 4 accepts the readonly tuple directly (`RESEARCH` L374-377). This is the schema-side half of CONTENT-05. `RESEARCH` Open Question 2 (L697-704): keeping `tipo` on `cases` is recommended (cheap, proves reuse) but droppable.

**Precise `min`/`max` numbers are Claude's discretion** (`CONTEXT`; `RESEARCH` L59). The values above are the `RESEARCH` proposal — adjust to the real design copy length, keep every field `min`-bounded so an empty string fails.

**Export:**
```typescript
export const collections = { services, process, differentiators, faq, cases };
```

**Absent by design:** no `type: 'content'`/`'data'`, no `entry.render()`, no `legacy.collections`, no `src/content/config.ts` (legacy path — use `src/content.config.ts`; `RESEARCH` L436-437, L662-667).

### `src/content/index.ts` (utility / read barrel, CRUD-read) — discretionary, recommended

**Structural source:** `RESEARCH` Pattern 3, L387-409.

**Full pattern:**
```typescript
import { getCollection } from 'astro:content';

const byOrder = (a: { data: { order: number } }, b: { data: { order: number } }) =>
  a.data.order - b.data.order;

export const getServices = async () => (await getCollection('services')).sort(byOrder);
export const getProcess = async () => (await getCollection('process')).sort(byOrder);
export const getDifferentiators = async () =>
  (await getCollection('differentiators')).sort(byOrder);
```

- `RESEARCH` Open Question 4 (L710-711): adopting this barrel is recommended; if the planner skips it, every consuming section must sort by `data.order` itself.
