<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo author → build pipeline | The case Markdown and its cover asset are authored in-repo by the maintainer and consumed by `astro sync` / `astro:assets` at build time. |
| local asset → image pipeline | `image()` resolves a path from content frontmatter into an importable asset. The resolved path is the only place content data influences the build's file access. |
| build output → visitor | Case strings and the optimized cover reach a visitor only after Phase 3 renders them. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-06 | Tampering | `cases.cover` / `image()` resolution | mitigate | `cover` resolves only the co-located `./dmarques-cover.webp` under `src/`. No remote image domain is configured in `astro.config.mjs` (`image.domains` / `image.remotePatterns` absent), so `image()` cannot fetch an external asset, and `public/` paths are rejected outright. Verified by `pnpm build` exiting 0 with no "Could not find requested image". |
| T-02-07 | Tampering | `cases.tipo` drifting from the form allow-list | mitigate | `tipo: z.enum(PROJECT_TYPE_VALUES)` imports the same tuple Phase 5 will use. A slug that is not in the allow-list fails `astro sync`, so content and the future form validator cannot diverge silently (CONTENT-05). |
| T-02-08 | Tampering (stored XSS, latent) | `problema` / `solucao` / `resultado` + the Markdown body | mitigate | The three structured fields are plain strings (D-09), so Phase 3 renders them as escaped text. The optional Markdown body is authored in-repo by the maintainer only and contains no raw HTML; Astro's Markdown pipeline does not enable `allowDangerousHtml`. Carried forward as a Phase 3 render-side control. |
| T-02-09 | Spoofing | dishonest portfolio claim | mitigate | CONTENT-03 / D-07: the single v1 entry is labeled `rotulo: projeto próprio` and its `resultado` cites only measured Phase 1 numbers from the CI lhci run. No fictional "demo" case ships. Felipe reviews the copy at the plan 02-03 checkpoint. |
| T-02-10 | Denial of Service | build-time image processing | accept | One 1600x1000 source image processed once by Sharp at build. Negligible build cost, no runtime image optimization (PERF-05: Vercel Image Optimization stays off). |
| T-02-SC | Tampering | npm/pnpm installs | mitigate | **Zero packages installed.** The cover is generated with the Sharp already bundled inside `astro@7.3.1` and resolved from the existing pnpm store — no new entry in `package.json` or `pnpm-lock.yaml` (asserted in every task's acceptance criteria). 02-RESEARCH.md § "Package Legitimacy Audit" records N/A for this phase. No `[ASSUMED]` / `[SUS]` package exists, so no legitimacy checkpoint is required. |

No High-severity threat is introduced by this plan: it adds no dependency, no inline `<script>`/`<style>`, no `style="` attribute, no secret, no serverless function and no third-party asset.
